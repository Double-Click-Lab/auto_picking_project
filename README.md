# 라즈베리파이 FastAPI 출고 서버

## 조회 전용 신호 모니터

```bash
cd /home/chan/server && env -u API_KEY python3 tools/signal_monitor.py
```

기존 메뉴형 테스트 프로그램과 별개입니다. 접속 기기의 첫 요청 IP, 주문 접수 내용과 순서, 장치 명령 준비·수신·완료, 상자 교체 대기, 앱의 새 상자 준비 완료 신호, 다음 주문 시작을 연속 표시합니다. 주문 전송·장치 제어·상자 준비 확인을 하지 않는 조회 전용 프로그램입니다. 상자 대기 안내를 한 번 출력한 뒤 새 이벤트가 없으면 조용히 기다립니다. 정상적인 반복 상태 조회와 모니터 자신의 요청은 출력하지 않으며, POST 등 변경 요청과 HTTP 오류는 표시합니다. IP는 기기의 요청 주소이며 실제 사람의 신원이나 지속 연결 상태는 아닙니다. 모의 장치 처리에는 `[모의 실행]`을 표시합니다.

모니터용 `GET /monitor/events?after=이벤트번호`는 `X-API-Key`가 필요하며, 서버 메모리에 최근 2000개 이벤트를 보관합니다. 시퀀스 순서로 중복 없이 읽고, 서버 재시작과 기록 누락을 안내합니다. 모니터 시작 전에 발생한 보관 기록도 표시합니다. 재시작 이전 이벤트는 보존하지 않습니다. 접수 이벤트의 품목은 검증·변환된 서버 품목 ID/수량이며 API 키와 원본 요청 본문은 기록하지 않습니다. 화면 시각은 모니터 컴퓨터의 현지 시간입니다.

다른 컴퓨터에서는 `python3 tools/signal_monitor.py --url http://서버IP:8000 --env-file /경로/.env`로 실행합니다. 기본 조회 간격은 1초이며 `--interval`로 조정할 수 있습니다. Ctrl+C로 모니터를 종료해도 서버 작업은 계속됩니다. 새 API 적용에는 서버 재시작이 필요하며, 주문 보존이 필요하면 먼저 아래의 초기화 옵션을 확인하세요.

## 사람의 상자 교체 확인 후 다음 주문 진행

현재 기본 동작은 `REQUIRE_BOX_CONFIRMATION=true`입니다. 아래의 기존 자동 완료 설명과 달리, 모든 주문은 물품 이송이 끝나면 `waiting_box` 상태에서 멈추며 마지막 주문도 확인을 받아야 `completed`가 됩니다. 모의 모드에도 같은 규칙을 적용합니다. 기존 자동 완료 방식은 이 옵션을 `false`로 설정하면 사용할 수 있습니다.

앱에서 주문 입력 시 앱 내부 리스트에 보관하고, **작업시작 버튼을 눌렀을 때** `POST /orders/app-inventor`로 리스트 전체를 전송하세요. 서버는 접수 즉시 입력 순서대로 처리합니다. 서버에 미리 접수한 주문을 별도의 시작 버튼까지 보류하는 기능은 없습니다.

1. 접수 응답(202)의 각 `order_id`를 저장합니다.
2. 기존처럼 1초마다 `GET /orders/{order_id}`를 조회합니다(`X-API-Key` 필요).
3. 응답의 `status`가 `waiting_box`이고 `box_replacement_required`가 `true`이면 앱에 **상자를 치우고 새 상자를 놓아 주세요**와 **새 상자 준비 완료** 버튼을 표시합니다. `progress.status_text`, `progress.events`에도 안내가 있습니다. HTTP 조회 방식이며 서버가 앱으로 직접 푸시하지는 않습니다.
4. 사람이 실제로 상자를 교체한 뒤 버튼을 누르면 **해당 대기 주문 ID**로 `POST /orders/{order_id}/box-ready`를 보냅니다. 본문은 필요 없으며 기존 `X-API-Key`를 사용합니다.
5. 성공 응답은 `200`과 `{"order_id":"...","status":"completed","accepted":true}`입니다. 그 후 작업자가 다음 대기 주문을 시작합니다. 다음 주문이 없으면 대기합니다.

`box-ready`는 같은 주문에 재전송해도 같은 성공 결과를 반환합니다. 이전 주문의 중복 확인은 다음 주문의 대기를 해제하지 않습니다. 아직 이송 중이거나 대기 중인 주문에 확인을 보내면 409, 없는 ID는 404, 키 불일치는 401입니다. 이송 중에 버튼을 활성화하거나 자동으로 확인 요청을 보내지 마세요. 한 주문 안의 상품/개별 물품 사이에는 교체하지 않고 **주문자 한 명의 전체 물품 이송 후** 교체합니다. 라인트레이서 신호는 보내지 않습니다.

테스트 프로그램의 6번 조회는 상자 대기에 도달하면 안내 후 메뉴로 돌아오며, 실제 교체 후 8번에서 해당 주문을 선택하고 확인하면 다음 주문으로 진행합니다. 앱과 테스트 프로그램의 확인은 같은 API를 사용합니다.

`CLEAR_ORDERS_ON_START=false`이면 상자 대기는 DB에 보존되어 재시작 후에도 확인 전까지 다음 주문을 막습니다. 현재 `.env`의 초기화 옵션이 true이면 재시작 시 주문·대기 상태가 모두 삭제됩니다. 대기를 보존하려면 재시작 전에 false로 변경하세요. 기존 실행 중인 서버에는 코드 변경 후 재시작이 필요합니다.

## 메뉴형 테스트 프로그램

서버를 실행한 상태에서 새 터미널을 열어 프로젝트 폴더에서 실행하세요. 테스트 도구는 Python 표준 라이브러리만 사용합니다.

```bash
python3 tools/test_client.py
```

다른 컴퓨터에서 접속할 때는 `python3 tools/test_client.py --url http://라즈베리파이IP:8000`으로 실행합니다. `.env`가 없는 컴퓨터에서는 서버에 설정된 `API_KEY`를 환경변수로 지정하세요. 도구는 프로젝트 루트의 `.env`에서 `API_KEY`를 자동으로 읽습니다. 이미 설정된 비어 있지 않은 환경변수 `API_KEY`가 있으면 환경변수를 우선 사용합니다. 다른 설정 파일은 `--env-file /경로/.env`로 지정할 수 있습니다. 시작 시 키 값 대신 설정 출처를 표시합니다.

| 메뉴 | 기능 |
|---|---|
| 1 | 서버 실행 모드, 오류, 작업자 상태 확인 |
| 2 | 등록된 품목과 보관함 위치 조회 |
| 3 | 통합 주문: 주문자 ID와 A~D 수량 입력 후 주문자를 계속 추가하거나 전체 전송 |
| 5 | 서버 저장 주문 목록 번호·주문자 ID·주문 ID로 상세 조회 |
| 6 | 1초마다 상태를 조회하고 완료/실패 시 결과 출력 |
| 7 | 최근 서버 접속 요청의 IP·시각·경로·응답 코드 확인 |

7번은 인증이 필요한 `GET /connections`에서 최근 HTTP 요청 최대 200건을 조회합니다. 서버 재시작 시 기록은 초기화됩니다. 인증 실패(401), 입력 오류(422)도 기록하며 API 키·요청 본문·쿼리 문자열은 저장하지 않습니다. 조회 자체는 기록에서 제외합니다. IP는 서버가 인식한 접속 주소이며 사람의 신원이나 현재 연결 여부를 뜻하지 않습니다. 프록시 환경에서는 프록시 또는 서버가 신뢰하는 전달 주소가 표시될 수 있습니다. 요청이 서버에 도달하지 않으면 기록되지 않습니다. 새 메뉴를 적용하려면 서버와 테스트 프로그램을 다시 실행하세요. 현재 주문 초기화 옵션이 켜져 있으면 서버 재시작 시 기존 주문이 삭제되므로 보관하려면 먼저 `CLEAR_ORDERS_ON_START=false`로 변경하세요.

처음에는 **1번에서 mode가 simulation인지 확인**한 뒤, 3번에서 주문자 ID와 A, B, C, D 수량을 차례로 입력하세요. 구매하지 않는 상품은 0을 입력합니다. 예를 들어 `person-1`, `2`, `0`, `0`, `1`을 입력하면 A 2개와 D 1개를 주문합니다. 인원수는 미리 입력하지 않습니다. 한 명의 입력이 끝나면 Enter로 다음 주문자를 추가하거나, s로 입력한 전체 주문을 전송하세요. b는 전송 없이 입력을 취소합니다. 한 명만 주문할 때도 같은 방식으로 s를 누르면 됩니다. 전송 전 화면에 실제 JSON이 표시됩니다.

3번 통합 주문은 `/orders/app-inventor`로 `{"request_id": "고유 ID", "orders": [["person-1", {"A": 2}, {"B": 0}, {"C": 0}, {"D": 1}]]}` 형식을 전송합니다. 수량은 0 이상의 정수이며 모두 0이면 다시 입력합니다. A~D는 ITEM-001~ITEM-004에 대응합니다. 서버 설정에 없는 상품은 미등록 안내와 함께 0으로 전송합니다. 예전 3개 품목을 사용하던 모의 서버는 최신 코드로 재시작하면 D가 한 번 자동 추가됩니다. 그래도 D가 미등록이면 서버의 `/configuration` API로 품목 등록 설정을 확인하세요. 테스트 프로그램에는 모터 길이·좌표 조회 및 설정 변경 메뉴가 없습니다.

접수 후 5번이나 6번으로 각 주문을 확인할 수 있습니다. 5번과 6번은 서버에 저장된 최근 주문 최대 100건을 불러오므로 도구를 재실행해도 번호로 선택할 수 있습니다. 주문자 ID로 검색할 수도 있으며 같은 주문자의 주문이 여러 건이면 검색 결과에서 번호를 선택합니다. 주문 ID 전체로 직접 조회하거나 b로 메뉴로 돌아갈 수도 있습니다.

모의 모드도 서버 DB에 주문·설정을 저장합니다. 실제 모드에 연결하면 주문은 실제 장치에 전달됩니다. Ctrl+C로 조회를 멈추거나 도구를 종료해도 서버 작업은 계속됩니다.

연결 상태만 빠르게 확인하려면 `python3 tools/test_client.py --check`를 실행하세요.

Ubuntu 22.04 / Python 3.10 이상. 앱 인벤터 주문을 SQLite에 저장하고 하나의 작업자가 장치를 순차 제어합니다. 기본값은 **모의 실행**이며 실제 GPIO, 모터 드라이버, 영상 인식, 로봇팔 펌웨어는 포함하지 않습니다.

## 서버 시작 시 주문 기록 초기화

현재 `.env`와 `.env.example`에는 `CLEAR_ORDERS_ON_START=true`가 설정되어 있습니다. 이 옵션을 켜면 서버 시작 시 완료·실패·대기·진행 주문, 장치 명령 이력, 앱 인벤터 request_id 중복 확인 기록을 모두 삭제합니다. 품목 목록과 모터 길이·좌표는 유지합니다. 변경된 `.env`를 다시 로드한 뒤 서버를 재시작하면 적용됩니다. 테스트 프로그램의 5번·6번에는 이번 서버 실행 이후 주문만 표시됩니다.

주문을 재시작 후에도 보관하려면 `CLEAR_ORDERS_ON_START=false`로 바꾸세요. 환경변수가 없을 때도 기본값은 false입니다. 아래의 주문 보존·재시작 복구 설명은 이 옵션을 끈 경우에 해당합니다. 초기화를 켜면 재시작 전 request_id를 다시 보내도 새 주문이 생성됩니다. 같은 서버 실행 중에는 기존 재전송 중복 방지가 유지됩니다. 주문자 customer_id는 원래부터 중복을 허용하며 주문별 request_id는 새로 발급해야 합니다.

실제 장치 모드에서 초기화해도 기존 장치 오류나 진행 주문의 재시작 오류는 자동 해제하지 않습니다. 이 경우 장치와 실제 출고 상태를 확인한 뒤 `/system/reset`으로 복구합니다. 초기화는 장치 정지 명령이 아닙니다.

## 실행

```bash
sudo apt update
sudo apt install python3-venv python3-pip
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
set -a
source .env
set +a
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

프로젝트 폴더에서 실행하세요. `.env`는 위 명령 또는 systemd가 로드합니다. `catalog.json`에 실제 품목 ID, 이름, 보관함 번호를 등록합니다. 수량은 1 이상의 정수이며 중복 품목 ID와 미등록 품목은 거절합니다. 품목 수와 주문자 수는 코드에 고정하지 않습니다. 재고 수량 및 실제 물건 존재 여부를 확인하는 기능은 아직 없습니다.

API 문서: `http://라즈베리파이IP:8000/docs`. 모의 실행 완료는 실제 출고 완료를 의미하지 않습니다. `/health`에서 실행 모드와 오류를 확인할 수 있습니다.

## 앱 인벤터

1. Web 컴포넌트의 `Url`을 `http://라즈베리파이IP:8000/orders`로 설정합니다.
2. `RequestHeaders`를 `[["Content-Type", "application/json"], ["X-API-Key", "설정한 앱 키"]]` 형태의 중첩 리스트로 설정합니다.
3. `PostText`로 다음 JSON 문자열을 전송합니다. 실제로는 딕셔너리/리스트를 만들고 `JsonObjectEncode`로 변환하면 됩니다.

```json
{
  "request_id": "phone1-order-20261104-001",
  "customer_id": "customer-001",
  "items": [
    {"item_id": "ITEM-001", "quantity": 2},
    {"item_id": "ITEM-002", "quantity": 1}
  ]
}
```

`202` 응답의 `order_id`를 저장한 뒤 Clock 컴포넌트로 1초마다 `GET /orders/{order_id}`를 호출합니다. JSON은 `JsonTextDecodeWithDictionaries`로 읽습니다. 상태는 `queued`, `running`, `completed`, `failed`입니다. `completed` 또는 `failed`이면 조회 타이머를 중지합니다. 접수 응답은 출고 완료 신호가 아닙니다.

통신 오류로 재전송할 때 **같은 request_id, customer_id와 같은 품목 목록**을 사용하면 기존 주문을 반환합니다. 새 주문에만 새 request_id를 발급하세요. 같은 ID로 다른 내용을 전송하면 `409`, 입력 오류는 `422`, 장치 오류 상태에서는 `503`을 반환합니다. `/items`에서 등록 품목을 조회할 수 있습니다.

## 실제 장치 연결 규약

`.env`에서 `SIMULATION=false`로 바꾸고 서로 다른 강력한 `API_KEY`, `DEVICE_KEY`를 설정합니다. 장치 제어 프로그램은 `X-Device-Key` 헤더를 넣어 다음 API를 주기적으로 조회합니다.

| 장치 | 명령 조회 | action | 성공 신호의 의미 |
|---|---|---|---|
| 리니어 모터 | `GET /devices/motor/commands/next` | `move_to_bin` | 해당 보관함으로 이동하고 정지함 |
| 카메라/정렬 제어기 | `GET /devices/camera/commands/next` | `align_bin` | 중앙 정렬을 확인했고 모터가 정지함 |
| 로봇팔 | `GET /devices/robot/commands/next` | `pick_and_place` | 물건 1개를 출고상자에 놓고 안전 위치로 복귀함 |

명령이 없으면 `{"command": null}`, 있으면 `command` 객체의 `id`, `action`, `payload`를 읽습니다. payload에는 `item_id`, `bin`, `position_mm`, `motor_length_mm`, `customer_id`, `order_id`, `destination_id`, `quantity: 1`, `destination: "shipping_box"`가 포함됩니다.

장치 동작이 **실제로 끝난 다음** `POST /devices/{device}/commands/{id}/complete`로 아래 결과를 보냅니다.

```json
{"success": true, "detail": "작업 완료"}
```

실패 시 `success: false`와 오류 설명을 전송합니다. 기본 제한 시간은 명령 생성 후 60초이며 `COMMAND_TIMEOUT`으로 변경합니다. 장치가 명령을 받았다는 이유만으로 성공 신호를 보내면 안 됩니다.

서버는 같은 명령 ID를 완료 신호가 올 때까지 계속 반환합니다. **장치 제어기는 명령 ID를 영구 저장해 중복 실행을 막아야 합니다.** 완료 응답이 유실되면 같은 결과를 재전송하세요. 장치당 조회 프로그램은 하나만 실행합니다. 카메라 제어기는 보정 이동과 정렬 확인을 담당하며, 정렬을 확인할 수 없으면 실패를 보고해야 합니다. 영상 인식 알고리즘과 보정값은 장치별 구현이 필요합니다.

품목마다 모터 이동 → 카메라 정렬 → 요청 수량만큼 로봇팔 1개 이송을 수행합니다. 같은 품목의 반복 이송에는 재정렬하지 않으므로, 보관함이 움직이지 않는 기구 구성이 전제입니다. 다음 품목부터 이동·정렬을 반복합니다. 마지막 이송 완료 신호를 받은 뒤 주문을 `completed`로 변경합니다.

## 오류와 복구

장치 실패/시간 초과 시 해당 주문을 실패 처리하고 전체 후속 처리를 멈춥니다. 서버 재시작 당시 진행 중인 주문도 실패 처리합니다. 대기 주문과 작업 이력은 DB에 유지됩니다. 실제 집은 수량을 알 수 없으므로 실패한 주문을 자동 재실행하지 않습니다.

운영자가 실제 출고 수량, 로봇팔 안전 위치, 보관함 위치와 장치 정지를 확인한 뒤 앱 키로 `POST /system/reset`을 호출하면 대기 주문 처리를 재개합니다. 부족분은 확인 후 새 주문으로 등록하세요. reset은 모터 정지 명령이 아닙니다. 서버 시간 초과만으로 실제 장치가 멈추지는 않으므로 장치 펌웨어에 로컬 시간 제한, 리미트 스위치, 비상 정지를 구현해야 합니다.

하나의 DB에 서버 프로세스 하나만 실행하도록 파일 잠금을 사용합니다. `--workers 1`을 유지하고 실제 운전 중 `--reload`를 사용하지 마세요. DB 파일은 백업하고 작업 이력을 운영 정책에 따라 보관하세요. HTTP 예제는 같은 신뢰할 수 있는 내부망용이며 외부 접속에는 HTTPS 구성이 필요합니다.

## 주문자별 일괄 접수

`customer_id`는 필수 주문자 식별자입니다. 기존 앱도 이 필드를 추가해야 합니다. 주문자 한 명당 하나의 주문을 만들며, 구매하지 않는 품목은 items에서 생략합니다(수량 0을 보내지 않습니다). 각 앱에서 `POST /orders`로 별도 접수하거나, `POST /orders/batch`로 다음처럼 여러 주문자를 한 번에 접수할 수 있습니다. 두 API 모두 `X-API-Key`를 사용합니다.

```json
{
  "orders": [
    {
      "request_id": "batch1-person1",
      "customer_id": "person-1",
      "items": [
        {"item_id": "ITEM-001", "quantity": 2},
        {"item_id": "ITEM-002", "quantity": 1},
        {"item_id": "ITEM-003", "quantity": 3}
      ]
    },
    {
      "request_id": "batch1-person2",
      "customer_id": "person-2",
      "items": [
        {"item_id": "ITEM-002", "quantity": 3},
        {"item_id": "ITEM-003", "quantity": 1}
      ]
    }
  ]
}
```

응답의 `orders` 배열에는 각 `order_id`, `customer_id`, `status`가 들어갑니다. 각 주문 ID로 완료 여부를 조회합니다. 일괄 접수는 배열 순서, 개별 접수는 서버 DB 접수 순서대로 처리합니다. 먼저 접수된 기존 주문이 있으면 그 주문부터 처리합니다. 여러 주문자의 물품을 교차 집거나 합치지 않습니다. 같은 주문자가 다시 주문해도 별도 접수 순서를 따릅니다. 일괄 요청 중 하나라도 잘못되면 해당 요청 전체를 저장하지 않습니다. request_id는 모든 주문자에 걸쳐 유일해야 합니다.

주문별 `destination_id`는 order_id입니다. **실제 출고상자를 자동으로 교체하거나 이동시키는 동작은 구현되어 있지 않습니다.** 장치 제어기가 이 ID에 맞는 상자를 준비하고 로봇팔의 `pick_and_place`를 처리해야 합니다. 공용 상자 하나를 계속 사용하면 주문자별 물품이 섞입니다.

## 가변 품목 및 리니어 모터 길이

처음 실행할 때 `catalog.json`과 `.env`의 `MOTOR_LENGTH_MM`(기본 1000mm)으로 설정을 만듭니다. `position_mm`는 모터 원점으로부터 해당 보관함의 이동 좌표이며, 예시 좌표는 실제 장치에서 측정한 값으로 바꿔야 합니다. 카메라는 이 위치에서 미세 정렬합니다. 장치도 동일한 원점·단위를 사용하고 이동 범위를 자체 검증해야 합니다.

초기 설정 이후에는 SQLite에 저장된 설정을 사용합니다. 파일을 수정해도 기존 DB 설정을 덮어쓰지 않습니다. `GET /configuration`으로 현재 설정을 읽고 `PUT /configuration`으로 아래와 같은 전체 설정을 전송해 변경합니다(`X-API-Key` 필요).

```json
{
  "motor_length_mm": 2000,
  "items": {
    "ITEM-001": {"name": "품목 1", "bin": "A01", "position_mm": 100},
    "ITEM-002": {"name": "품목 2", "bin": "A02", "position_mm": 800},
    "ITEM-003": {"name": "품목 3", "bin": "A03", "position_mm": 1600},
    "ITEM-004": {"name": "추가 품목", "bin": "A04", "position_mm": 1900}
  }
}
```

품목은 전체 목록 교체 방식으로 추가·수정·삭제하며 모터 길이를 균등 간격으로 자동 나누지 않습니다. 각 보관함의 실제 위치를 입력하세요. 위치는 0~motor_length_mm 범위여야 합니다. 범위를 벗어나면 `422`, 대기·진행 주문이나 미복구 오류가 있으면 `409`를 반환합니다. 주문에는 접수 당시 설정도 저장합니다.

기존 DB는 시작 시 필요한 열을 추가하며, 기존 주문의 주문자 ID는 `legacy`로 표시합니다. 기존 진행 주문에 대한 재시작 실패 처리는 유지됩니다. 주문자와 품목 개수에는 고정 상한을 두지 않았지만 실제 처리 용량은 라즈베리파이의 메모리·디스크와 장치 속도에 따릅니다.


### 테스트 도구에서 HTTP 401이 발생할 때

`/health`는 인증 없이 조회할 수 있어 1번만 정상이고 다른 메뉴는 401일 수 있습니다. 서버와 테스트 도구의 API_KEY를 일치시키세요. 현재 도구는 `.env`를 자동으로 읽으므로 먼저 도구를 종료하고 다시 실행해 보세요.

```bash
python3 tools/test_client.py
```

환경변수에 이전 키가 남아 있으면 다음처럼 해당 실행에서만 환경변수를 제거해 `.env`의 키를 사용하세요.

```bash
env -u API_KEY python3 tools/test_client.py
```

계속 401이면 실행 중인 서버가 다른 키를 사용 중일 수 있습니다. 진행 중인 주문이 없을 때 서버를 종료하고, 서버 터미널에서 프로젝트의 `.env`를 다시 불러온 뒤 실행하세요. 실제 장치 운전 중 서버를 재시작하면 진행 주문은 실패 처리됩니다.

주문 목록 조회 API는 `GET /orders`이며 `customer_id`(정확히 일치), `limit`(1~100), `offset`으로 검색·페이지 조회가 가능합니다. 기존 서버가 실행 중이면 진행 주문이 없는 상태에서 서버를 재시작해야 새 조회 API가 적용됩니다.


## A~D 수량 입력과 한글 진행 상황

3번 통합 주문 입력에서는 A, B, C, D 순서대로 서버에 등록된 이름과 품목 ID를 표시하고 수량을 입력받습니다. 구매하지 않는 상품은 0을 입력하세요. 서버에는 네 상품 딕셔너리를 모두 포함한 리스트를 전송합니다.

5번은 한글 주문 요약과 단계별 기록을 표시하고, 6번은 1초마다 새 기록만 출력합니다. 예:

```text
[모의 실행] 품목 1 (ITEM-001): 리니어 모터에 신호를 주었습니다.
[모의 실행] 품목 1 (ITEM-001): 리니어 모터 이동 완료 신호를 받았습니다.
[모의 실행] 품목 1 (ITEM-001): 카메라로 보관함을 확인했습니다.
[모의 실행] 품목 1 (ITEM-001): 로봇팔로 물건 1개를 출고상자에 옮겼습니다.
[모의 실행] person-1 주문자의 물품을 출고시켰습니다.
```

실제 모드에서는 명령 생성만으로 신호 전달 완료를 표시하지 않습니다. 장치가 명령 조회 API에서 명령을 가져오면 전달 기록을 남기고, 완료 API로 성공 결과를 보내면 확인·이송 완료 문구를 표시합니다. 명령 ID별 전달 시각과 완료 시각도 DB에 저장됩니다. 이전 기록에 시각 정보가 없으면 임의로 채우지 않습니다. 주문 조회 API의 `progress.status_text`, `progress.events`에 같은 한글 기록이 들어 있으므로 앱에서도 사용할 수 있습니다. 이벤트 ID로 중복 표시를 막을 수 있습니다.

현재 통신은 HTTP 명령 조회/완료 보고 방식이며 ROS·MQTT 토픽 발행/구독은 구현되어 있지 않습니다. 이 출력은 해당 토픽의 송수신을 입증하지 않습니다. 향후 토픽 어댑터를 연결할 때 실제 명령 전달과 완료 수신을 이 기록에 연결해야 합니다. 변경 적용에는 서버와 테스트 도구를 모두 재시작해야 합니다.

## 앱 인벤터 A~D 리스트 접수

`POST /orders/app-inventor`에 `Content-Type: application/json`, `X-API-Key` 헤더를 사용합니다.
앱 인벤터의 딕셔너리와 리스트를 만든 뒤 `JsonObjectEncode`로 아래 전체 객체를 JSON으로 변환해 `PostText`로 전송하세요.

```json
{
  "request_id": "phone1-batch-20261109-001",
  "orders": [
    ["person-1", {"A": 2}, {"B": 0}, {"C": 0}, {"D": 1}],
    ["person-2", {"A": 0}, {"B": 1}, {"C": 3}, {"D": 0}]
  ]
}
```

각 안쪽 리스트는 ID와 A, B, C, D 딕셔너리 순서로 정확히 5개입니다. JSON/Python 인덱스는 0~4이지만 **앱 인벤터 리스트 블록의 인덱스는 1~5**입니다. 주문자 수는 가변이며 한 명일 때도 바깥 리스트로 감쌉니다. 각 딕셔너리는 `{"A": 2}`처럼 상품명 하나를 키, 수량을 값으로 사용합니다. 수량은 0 이상의 JSON 정수로 보내며 문자열, 소수, 음수, 불리언은 거절합니다. 수량 0은 이송에서 제외하며 전부 0인 주문자는 거절합니다. 잘못된 행이 하나라도 있으면 전체 접수를 취소합니다.

상품 매핑은 A→ITEM-001, B→ITEM-002, C→ITEM-003, D→ITEM-004입니다. 초기 catalog.json에는 네 품목이 있지만 **기존 SQLite 설정은 일반적으로 자동 변경되지 않습니다. 다만 모의 실행에서 예전 ITEM-001~ITEM-003만 저장된 DB는 서버 시작 시 한 번 D를 catalog.json에서 추가합니다. 기존 품목·모터 길이는 유지하며 D 좌표가 모터 길이 이내일 때만 추가합니다. 이후 의도적으로 삭제한 D는 재시작해도 복구하지 않습니다. 실제 장치 모드에서는 자동 추가하지 않습니다**. 기존 서버는 대기·진행 주문이 없고 오류가 해제된 상태에서 `GET /configuration` 결과에 ITEM-004를 추가하고 A~D 이름 및 실제 보관함 좌표를 확인한 뒤 `PUT /configuration`으로 전체 설정을 저장하세요. 예시 좌표는 실제 측정값이 아닙니다. 수량이 양수인 상품이 설정에 없으면 422로 전체 거절합니다.

새 전송마다 고유한 request_id를 만들고, 응답 유실 시 같은 ID와 전체 내용을 그대로 재전송합니다. 같은 ID로 주문자 수·순서·내용을 바꾸면 409입니다. 재전송은 기존 주문 ID들을 반환합니다. 응답은 기존 일괄 접수처럼 `{"orders": [{"order_id": "...", "customer_id": "person-1", "status": "queued"}]}`이며 각 ID를 `GET /orders/{order_id}`로 조회합니다. 접수 순서대로 기존 모터→카메라→수량만큼 로봇팔 흐름을 실행합니다.

새 앱 구조를 선택할 수 있다면 위치에 의존하는 리스트보다 기존 `/orders/batch`의 `customer_id`, `request_id`, `items` 객체 형식을 권장합니다. 구매한 상품만 items에 넣으면 상품 추가나 순서 변경에 유연하고 각 주문의 재전송도 독립적으로 처리할 수 있습니다. 이 경우 수량 0은 생략하고 실제 item_id를 보냅니다.
